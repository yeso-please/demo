## A. 이 앱은..

**"국내 여행의 쏠림을 해소하는 발견 플랫폼"** → 거창.. 하지만 담고 싶은 가치

→ 여행자·지역 소상공인·지자체 셋 다 "덜 알려진 곳이 안 알려진다"는 같은 문제를 겪는다..
→ 3자 가치를 다 담을 수 있으면 좋지만 없다면..? 최대한 겹치는 부분을 찾자

**겹치는  지점 = 시군구 코드(SIG_CD) 한 개**
→ 여행자는 그 코드로지역을 열고, 소상공인은 그 코드 아래 노출되고, 지자체가 푼 공공데이터도 그 코드로 묶인다
→ 하나의 키가 셋을 동시에 만족시킨다. 여기서 출발하자

## B. 만들면서 회고하면서..

**공공데이터는 이미 충분히 있다**
→ 250개 시군구 **전부**에 관광지가 있다(6,769곳). 음식점 8,540곳, 착한가격업소 12,106곳
→ 정보가 없어서 안 가는 게 아니다.. **닿는 채널이 없어서** 안 간다
→ 문제는 데이터가 아니라 **발견 경험**이라는 게 실측으로 확인됨

**"검색"은 쏠림을 재생산한다**
→ 포털·SNS·여행앱은 전부 검색량/리뷰수/예약수로 정렬 → 노출된 곳에 데이터가 더 쌓임
→ 우리가 랭킹 UI를 넣는 순간 똑같은 서비스가 된다..
→ 그래서 지도를 기본 UI로 두고 **모든 지역이 같은 크기의 진입점**을 갖게 함

**애초에 랭킹을 만들 데이터가 없다 (역설적으로 다행)**
→ TourAPI에 평점·리뷰수·혼잡도가 **없음**. "인기순", "평점 4.5↑" 같은 UI는 만들 수가 없다
→ 처음엔 제약이라고 생각했는데.. 방향과 오히려 맞아떨어짐

**지역 소개글이 API에 없다는 걸 뒤늦게 확인**
→ `areaCode2` 응답이 `rnum, code, name` 뿐.. 서사형 문단을 큰 자리로 잡으면 채울 수가 없음
→ 초기엔 "안동은 정신문화의 수도로.." 같은 목업을 넣어놨었는데 전부 걷어냄
→ **가진 숫자로 문장을 조립**하는 쪽으로 선회 (관광지 69곳·음식점 20곳·착한가격업소 44곳..)

**상세 설명은 API 한도에 막힌다**
→ 관광지 1건당 호출 2회, 6,769건 채우면 13,000회.. **1일 한도 1,000회**라 2주 소요
→ 전량 선적재를 포기하고 **사용자가 펼쳐 본 것만** 가져와 영구 저장하는 방식으로 변경
→ 이 결정이 화면 설계를 바꿈: 설명이 처음부터 있다고 전제할 수 없다 → "자세히" 펼치기 + 로딩 상태 필수

**특산물은 10%밖에 없다**
→ 250곳 중 24곳. 처음엔 특산물을 지역 정체성의 축으로 잡았는데 대부분 지역에서 섹션이 통째로 사라짐
→ 없으면 사라지는 걸 **예외가 아니라 기본**으로 두고 설계

**초기 온보딩(취향 2문항)은 아무것도 하지 않았다**
→ "잘 안 알려진 곳 / 잔잔한 곳" 2문항을 받아놓고 **수집만 하고 어디에도 안 씀**..
→ 재미도 없고 쓰이지도 않으니 진입 마찰만 늘리는 화면이었음
→ **여행 MBTI 12문항으로 교체**하고, 결과가 실제로 쓰이는 자리를 세 군데 만듦 (프로필·후기·AI 상담)

**사용자 데이터가 비어 있다는 게 가장 큰 현실**
→ 후기 1건, 코스 소량.. 후기 피드는 **빈 상태가 사실상 기본 화면**이다
→ 카드가 가득 찬 그리드만 디자인하면 실제로는 그 화면을 볼 일이 없음
→ 빈 상태를 첫인상으로 다뤄야 함

**아직 없는 것: 실제 사용자 리서치**
→ 위 근거는 전부 **데이터 실측과 구현 과정에서 나온 것**이지 설문·인터뷰가 아니다
→ "반복 여행에 지쳤다"는 페르소나 전제는 아직 **검증되지 않은 가설**이다 (→ 08 참고)

# [PRD] 시군구 코드 기반의 국내 여행 발견 플랫폼: 숨은여행 (Sumeun)

## 01. Problem (문제 정의)

**여행자**: **목적지가 정해져야 검색이 시작되는데, 그 첫 단계에 도구가 없다.** "국내여행 추천"을 검색하면 광고성 리스트가 나오고 결국 늘 가던 곳(제주·부산·강릉·경주)을 고른다. 낯선 지역을 후보에 올려도 관광지는 A 사이트, 맛집은 블로그, 물가는 알 수 없어 탭 10개를 열다 포기한다. 특히 **가격을 예측할 수 없어** 바가지 우려가 회피 요인이 된다.
→ **첫 화면에서 이탈한다..**

**지역 소상공인**: 착한가격업소로 등록해 가격을 공개해도 **닿을 채널이 없다.** 검색 상위는 이미 유명한 곳이 차지한다.
→ 여행자와 겹치는 부분 많음 — 한쪽은 믿을 가격 정보를 못 찾고, 한쪽은 가진 정보를 못 보여준다

**지자체·공공기관**: TourAPI·착한가격업소로 데이터를 개방했지만 **소비 지점이 없다.** 데이터는 있는데 여행 수요로 전환되지 않는다.

---

## 02. Target User (핵심 사용자 정의)

**주요 사용자 (여행자)**: 갈 만한 데는 대충 다 가봤다는 감각이 있고, SNS에 안 나온 곳을 선호하지만 직접 발굴할 리서치 체력은 없는 **20~30대 1~2인·커플 여행자**. 주말/연휴 2~3주 전, **목적지 미정 상태**에서 막연히 탐색을 시작한다.

**보조 사용자 (후기 작성자)**: 다녀온 코스를 기록으로 남기고 싶은 사용자. 공공데이터가 채우지 못하는 **"가볼 만한가"라는 주관적 판단**을 공급한다. 여행자와 같은 사람이지만 **여행 후(後) 시점**의 다른 역할이다.

**이해관계자 (지역 소상공인·지자체)**: 착한가격업소 표에 업소명·메뉴·가격이 그대로 노출되는 것이 직접적인 가치. *다만 현재 서비스와 계약·정산 관계는 없다 — 데이터를 인용할 뿐이다.*

---

## 03. Solution Concept (솔루션 컨셉)

> **"랭킹 없는 지도에서 목적지 없이 시작해, 시군구 코드 하나로 조립된 지역 정보를 보고, 나만의 코스로 완성하는 서비스"**

**설계 원칙 3가지**

1. **목적지가 없는 상태에서 시작한다.** 기존 서비스는 "안동 검색"부터 시작하지만, 우리는 **"어디로 갈까?"** 상태를 첫 진입점으로 삼는다 → 지도 클릭 · 랜덤 룰렛 · AI 상담
2. **검색이 아니라 지도로 탐색한다.** 리스트/랭킹은 쏠림을 재생산한다. 전국 250개 시군구 폴리곤을 기본 UI로 두어 **모든 지역이 동등한 진입점**을 갖는다
3. **한 지역의 정보는 한 화면에 모은다.** 관광지·먹거리·착한가격업소·특산물·추천 코스를 **SIG_CD 하나로 조인**해 단일 번들로 제공한다

---

## 04. Core Features & Value (핵심 기능 및 사용자의 불안 해소)

### 1순위: 랭킹 없는 탐색 엔진 (발견 중심)

**기능 1. 전국 시군구 탐색 지도** — 검색창 대신 250개 폴리곤. 클릭하면 우측 패널에 요약(특산물·착한가격업소·추천 반일 코스)이 슬라이드로 뜬다. **정렬도 순위도 없다.**
→ 검색어를 몰라도 탐색이 시작된다. 쏠림을 UI 차원에서 구조적으로 차단

**기능 2. 랜덤 여행지 룰렛** — 여러 지역이 순차로 점멸하다 한 곳에서 멈춘다(3~4초).
→ "아무 데나 좋으니 새로운 곳" 니즈에 즉답. 선택 피로 자체를 없앤다

**기능 3. 통합 지역 상세** — 지표 4종(관광지/맛집/착한가격업소/특산물 수) · 지역 소개 · 추천 코스 카드 · 착한가격업소 표 · 카카오맵 길찾기.
→ 파편화된 정보를 한 화면으로 통합. **숫자 지표로 "여기 볼 게 있나"를 즉시 판단**하게 함

**기능 4. 착한가격업소 가격 공개** — 업소명·메뉴·가격·주소를 행정안전부 데이터 그대로 노출.
→ **낯선 지역의 최대 회피 요인인 가격 불확실성을 공식 데이터로 해소.** 유명 지역이 못 가진 우리만의 근거

### 2순위: 성향 기반 매칭 (개인화 중심)

**기능 5. 여행 MBTI 진단(12문항)** — 계획성(J/P) 4문항 · 정보 해석(S/N) 2문항 · 판단 기준(T/F) 3문항 · 에너지(E/I) 3문항 → 16유형.
→ 초기 설정 단계에서 취향을 **재미있게** 수집. 결과가 실제로 세 군데에서 쓰인다

**기능 6. AI 여행 상담** — 자연어로 물으면 지역·코스를 추천하고 **이동 버튼**을 함께 준다. 로그인 상태면 MBTI 성향을 프롬프트에 반영한다.
→ *"마음에 담는 몽상가인 INFP 성향에 어울리는 고요한 영월군을 추천해 드려요"*
→ **모델이 지어내지 못하게** DB 실재 목록만 프롬프트에 넣고, 응답 ID를 다시 DB로 검증한 뒤에만 버튼을 만든다

**기능 7. 오늘의 숨은 여행지** — 지역 미선택 시 좌측에 카드 무한 스크롤.
→ 아무것도 안 눌러도 발견이 계속 일어난다

### 3순위: 실행과 순환 (리텐션 중심)

**기능 8. 내 코스 만들기** — 좌측 후보(관광지/먹거리/착한식당/특산물)에서 담아 우측 타임라인 구성, 드래그로 순서 변경.
→ 발견에서 끝나지 않고 **실행 가능한 결과물**로 연결

**기능 9. 실제 도로 경로 표시** — 저장 시 카카오모빌리티로 경로를 1회 계산해 저장. 지도에 선·화살표가 순서대로 그려진다.
→ 메모장+지도앱 수작업을 대체. *한도 때문에 편집 중에는 계산하지 않는다*

**기능 10. 후기 작성·공유·피드** — 사진 5장 + 줄글 + 공개 여부. 상세는 공유 링크의 대상이고, 피드에서 남의 후기를 본다. **작성자 MBTI 뱃지가 붙는다.**
→ **탐색 루프를 닫는 기능.** ① 다녀온 뒤 돌아올 이유가 생기고 ② 남의 후기가 곧 덜 알려진 지역의 콘텐츠가 된다
→ 후기 상세에는 항상 "이 지역 보기 / 코스 만들기" 복귀 경로를 둔다. **후기는 읽고 끝나는 글이 아니라 다음 여행의 진입점이다**

### 가치 요약

| 사용자 문제 | 대응 기능 | 전달 가치 |
|---|---|---|
| 어디로 갈지 모름 | 기능 1·2·6·7 | 목적지 없이 시작 가능한 탐색 |
| 정보 파편화 | 기능 3 | 지역당 단일 통합 화면 |
| 가격 불확실 | 기능 4 | 공식 데이터 기반 가격 신뢰 |
| 동선 수작업 | 기능 8·9 | 담기 → 경로 → 완성 |
| 재방문 이유 없음 | 기능 5·10 | 남의 후기가 새 지역의 발견 입력이 됨 |

## 05. User Flow (사용자 흐름)

**여행자(신규·목적지 미정)**: 앱 실행 ➔ 회원가입 ➔ **여행 MBTI 12문항** ➔ 지도에서 지역 클릭 / 룰렛 / AI 상담 ➔ 우측 패널 요약 확인 ➔ 지역 상세에서 지표·착한가격업소 가격 확인 ➔ 후보 담아 코스 구성 ➔ 저장 ➔ **경로·거리·시간 확인**

**여행 후(後)**: 내 코스 ➔ 후기 작성(사진+줄글+공개 여부) ➔ 후기 상세 ➔ **링크 복사해 공유**

**발견 루프(다른 사람 → 나)**: 후기 피드 ➔ 후기 상세(작성자 MBTI 뱃지) ➔ **"이 지역 보기"** ➔ 지역 상세 ➔ 코스 만들기 ➔ 다시 저장 ➔ 다시 후기

> 이 루프가 기능 10의 존재 이유다. 공공데이터는 **"무엇이 있는지"**를 알려주지만
> **"가볼 만한지"**는 다녀온 사람만 알려줄 수 있다.

**예외 흐름** — 데이터 미적재 지역 → 빈 상태 UI · 위치 권한 거부 → 목적지만으로 길찾기 · 남의 코스/비공개 후기 접근 → 리다이렉트 · API 한도 소진 → 설명 없이 이름·주소·사진만

## 06. Success Metrics (가장 중요한 한 가지 성공 지표)

### **"낯선 지역 코스 완성률"**

사용자가 **한 번도 고려해본 적 없던 시군구**를 앱 안에서 발견해 코스로 저장했는지 측정.

**정의**: 신규 가입자 중 7일 이내에 [목적지 미정 진입 ➔ **비(非)유명 시군구** 상세 진입 ➔ 코스 저장]까지 이탈 없이 마친 비율 **20% 달성**
*비유명 = 검색량 상위 20개 시군구(제주·부산·강릉·경주 등)를 제외한 나머지 230곳*

**이유**: 이 서비스의 존재 이유는 "쏠림 해소" 하나다. 사용자가 유명 지역을 고르면 우리가 아니어도 됐던 여정이고, 발견만 하고 저장하지 않으면 실행으로 이어지지 않은 구경이다. **처음 보는 지역을 실제 계획으로 바꿨을 때만** 문제 정의가 증명된다.

**보조 지표** — 탐색된 고유 시군구 수/세션 · 착한가격업소 항목 클릭률(가격 근거의 실효성) · 코스 저장 → 후기 작성 전환율 · **후기 열람 → 그 지역 상세 진입률**(발견 루프 가설)

## 09. AI 여행 상담 — 구현 방식 검토 (선택 논의 사항)

### 후보

**01. LLM API 호출** *(현재 방식)*
→ Gemini 무료 등급으로 호출. 프롬프트에 지역·코스·사용자 정보를 넣어 준다
→ 장점: 구현 간단, 모델 품질 높음, 서버 운영 부담 없음

**02. 모델 직접 구현**
→ 학교 GPU 서버(세라프)에 모델을 올려 데이터를 학습시키고, **하루 뒤 학습된 모델을 다운로드**
→ 상시 서빙이 아니라 **배치 작업**이다. 서버가 내려가도 서비스는 영향받지 않는다
→ 사용 가능 기간 약 2개월

> **MCP 로 백엔드와 통신하는 안은 접었다.** MCP 는 *모델에 도구를 붙이는* 프로토콜이지
> 모델을 서빙하는 프로토콜이 아니다. 자체 모델 서빙은 vLLM/Ollama 의 OpenAI 호환 HTTP 가 표준이다.
> *"모델이 우리 DB 를 직접 조회하게 한다"*가 목적이라면 그건 함수 호출(function calling) 패턴이고
> **Gemini 도 이미 지원한다** — 01/02 선택과는 무관한 축이다.

**넣을 수 있어도 넣으면 안 된다**
→ 매 질문마다 100만 토큰을 태우면 **무료 한도가 몇 번 만에 소진**된다. 지금은 질문당 1.3만 토큰이라 여유가 있다
→ 프롬프트가 길수록 응답이 느려진다. 상담 UX에서 체감 지연은 치명적
→ 긴 컨텍스트에서는 **중간에 묻힌 항목의 회상률이 떨어진다.** 250개는 잘 찾지만 25,000개는 안정적으로 못 찾는다

### 그래서 지금 방식의 진짜 한계는 따로 있다

한도가 아니라 **카탈로그에 무엇을 넣었느냐**다. 현재 프롬프트에는 **지역 250개와 여행코스 347개만** 들어간다.

→ 관광지 6,769곳은 **지역별 개수만** 들어간다 → *"월영교 같은 데 있어?"* 에 답할 수 없다
→ 착한가격업소는 **아예 없다** → 우리 차별점인 가격 정보를 챗봇이 못 쓴다

**즉 필요한 건 "다 넣기"가 아니라 "질문에 맞는 것만 골라 넣기"다.**
→ 1차: 질문 → 지역 후보 3~5곳 선별 → 2차: **그 지역의 관광지·착한가격업소만** 프롬프트에 추가
→ 후보 50개면 2만 토큰 남짓. 지금 예산 안에서 관광지 단위 추천까지 커버된다
→ **선별 방법은 10절(임베딩 + 코사인 유사도)에서 정한다**

## 10. 임베딩 + 코사인 유사도 추천 (채택 방향)

> 사용자 질문을 임베딩해 **코사인 유사도**로 비슷한 대상을 찾고, 그 후보만 프롬프트에 넣어
> Gemini 가 답변을 쓴다. 09에서 필요하다고 본 "선별 주입"의 구체적인 방법이다.

### 세라프에서 할 일은 "학습"이 아니라 "임베딩 계산"이다

→ 코사인 유사도 검색에 **파인튜닝은 필요 없다.** 사전학습된 한국어 임베딩 모델을 그대로 쓰면 된다
→ 파인튜닝하려면 *(질문, 정답 코스)* 쌍이 있어야 하는데 **우리에겐 한 건도 없다.** 서비스를 열어 클릭 로그가 쌓인 다음의 이야기다
→ 세라프에서는 **6,769건을 한 번에 임베딩**하고, 나온 **벡터와 모델을 받아온다.**
  "올려서 하루 뒤 받아온다"는 배치 방식과 정확히 맞는다 — 상시 서빙이 아니므로 서버 가용성 문제도 없다

**질의 임베딩은 실시간이어야 한다** — 여기가 설계의 핵심 제약
→ 사용자 질문은 미리 계산할 수 없고, **문서와 같은 모델**로 임베딩해야 벡터를 비교할 수 있다
→ 그래서 세라프에서 **모델 자체를 받아 앱 서버에 두고** 질문만 그때그때 임베딩한다
→ 짧은 질문 1건은 CPU 추론으로도 충분하다. GPU 상주가 필요 없다

### 저장·검색에 벡터 DB는 필요 없다

| | 계산 |
|---|---|
| 벡터 크기 | 6,769건 × 1,024차원 × 4바이트 = **약 26MB** |
| 전수 비교 비용 | 6,769 × 1,024 = **693만 회 곱셈** → 자바로 수 ms |

→ 메모리에 올려두고 전부 비교해도 된다. **pgvector·FAISS는 수백만 건부터 의미가 있다**
→ 지금 도입하면 과설계다. 나중에 느려지면 그때 바꿔도 늦지 않다

### 무엇을 임베딩할 것인가 — 재료를 재봤다

**여행코스를 임베딩하려던 계획은 재료가 없다.**

| 대상 | 보유 | 임베딩 재료 |
|---|---:|---|
| 여행코스 | 347 | **제목 평균 20.5자 + 테마.** 설명 컬럼 자체가 없음 |
| └ 경유지 있는 코스 | **27 (8%)** | 나머지 320개는 제목 20자가 전부 |
| 관광지 | 6,769 | 이름·주소 + **설명 평균 407자** (현재 37건, 수집 예정) |
| └ 대표 이미지 | 6,365 (94%) | |

→ 코스 92%가 **20자 제목뿐**이다. 이걸 임베딩해 코사인 유사도를 재면 사실상 키워드 매칭이고, 유사도 점수는 의미가 없다
→ **관광지가 훨씬 좋은 재료다.** 설명 407자면 "고요한", "혼자 걷기 좋은" 같은 질문이 실제로 걸린다

**그래서 관광지를 임베딩하고, 코스는 우리가 조립한다.**
→ 질문 → 유사한 관광지 N곳 → 지역별로 묶어 코스 제안
→ 이미 **내 코스 만들기가 관광지를 조립하는 UI**다. 챗봇이 관광지를 골라주면 그대로 코스가 된다
→ TourAPI 코스는 92%가 경유지도 없어서 원래 그대로 추천하기 어려웠다

### 관광지 설명 수집은 2개월이면 충분하다 (실은 2주)

| | |
|---|---|
| 필요 호출 | 6,769건 × 2회 = **13,538회** |
| 1일 한도 | 1,000회 (950 가드) |
| 소요 | **약 15일** |

→ 2개월 기간 안에 여유 있게 끝난다. **이게 임베딩 품질을 좌우하므로 가장 먼저 시작해야 한다**
→ 지금은 사용자가 펼쳐 본 것만 모으는 방식(37건)이라, **선적재 배치를 따로 돌려야 한다**
→ 설명이 없는 관광지도 나올 수 있다. 그건 이름·주소만으로 임베딩하고 **점수를 낮게 준다**

### 임베딩만으로는 부족하다 — 필터와 같이 쓴다

→ 코사인 유사도는 *"조용하고 물 있는 데"* 같은 **분위기**에 강하고, *"안동"*, *"3만원 이하"* 같은 **정확한 조건에 약하다**
→ 지역·가격·카테고리는 **SQL 로 먼저 거르고**, 그 안에서 임베딩으로 정렬한다
→ 여행 MBTI 성향도 같은 방식으로 후보 가중치에 반영할 수 있다

### 정리하면 이 구조다

```
질문 "조용하고 사람 적은 데서 걷고 싶어"
   ↓ 앱 서버에서 실시간 임베딩 (세라프에서 받아온 모델)
   ↓ SQL 필터(지역·카테고리) → 후보 축소
   ↓ 코사인 유사도 상위 N곳          ← 세라프가 미리 계산해 둔 벡터
[관광지 후보 30~50곳] ≈ 2만 토큰
   ↓ 프롬프트에 이것만 넣는다
Gemini → 답변 + 코스 제안
   ↓ 응답 ID 를 DB 로 재검증          ← 기존 안전장치 유지
[이동 버튼]
```

→ 검색은 우리 것, 생성은 Gemini. **각자 잘하는 쪽을 맡는다**
→ 09에서 잰 토큰 예산(현재 1.3%) 안에 관광지 단위 추천까지 들어온다

### 남은 판단과 확인할 것

| 항목 | 상태 |
|---|---|
| 임베딩 모델 선정 (한국어) | 후보 비교 필요 — 차원 수가 저장·속도를 좌우 |
| 관광지 설명 선적재 배치 | **미착수. 15일 걸리므로 가장 먼저 시작** |
| 무료 등급 분당 토큰 한도(TPM) | 미측정. 후보 주입으로 프롬프트가 커지면 동시 사용자에서 먼저 막힐 수 있음 |
| LLM 자체를 세라프에 올리기 | 하지 않는다 — 배치라 상시 서빙이 안 되고, 한국어 소형 모델 품질이 Gemini Flash 보다 낮다 |
| 임베딩 모델 파인튜닝 | **한다.** 학습쌍을 만드는 방법이 있다 → 11절 |

## 11. 무엇을 학습시킬 것인가

> 10절에서 "파인튜닝은 학습 데이터가 없어 불가능"이라고 적었는데, **학습쌍을 만드는 방법이 있어** 다시 정리한다.
> 앞서 "필요 없다"고 한 것은 **LLM 에 사실 지식을 주입하는 파인튜닝**이고, 검색 모델 학습은 다른 이야기다.

### 학습이 실제로 이 프로젝트를 개선하는 자리

| # | 과제 | 무엇을 고치나 | 임팩트 |
|---|---|---|---|
| **T1** | **임베딩 모델 도메인 적응** | 일반 한국어 모델은 관광 어휘를 모른다 | **핵심 경로 — 추천 품질 직결** |
| **T2** | **리랭커(cross-encoder) 학습** | 상위 50개의 순서를 다시 매긴다 | T1 다음 단계 |
| T3 | 사용자 로그 기반 재학습 | 실제 클릭을 정답으로 | **지금은 불가** (로그 0건) |

---

### T1. 임베딩 모델 파인튜닝 — 학습쌍은 만들면 된다

**문제**: *(질문, 정답 관광지)* 쌍이 0건이다. 서비스를 아직 안 열었으니 클릭 로그가 없다.

**해법 — 질의 생성(query generation)**
→ 관광지 설명을 Gemini 에 주고 **"이곳을 찾는 사람이 할 법한 질문 3개"**를 만들게 한다
→ *"고요한 자연에서 혼자 걷기 좋은 곳"* ← 월영교 설명에서 생성
→ 이렇게 만든 *(생성 질문, 그 관광지)* 를 **정답 쌍**으로 쓴다
→ 검색 학습 데이터가 없을 때 쓰는 표준 기법이다 (Doc2Query · GPL 계열)

| | |
|---|---|
| 생성 비용 | 관광지 6,769건 × 1회 = **6,769 호출** → 무료 한도로 **1~2주** |
| 만들어지는 학습쌍 | 6,769 × 3 = **약 20,000쌍** |
| 학습 방식 | 대조 학습(contrastive) — 같은 배치의 다른 관광지를 오답으로 씀 |
| 학습 장소 | **세라프.** 올려서 하루 뒤 모델 다운로드 — 배치 방식과 정확히 맞는다 |

**측정 방법 (이게 중요하다)**
→ 생성한 질의의 **10%(약 2,000쌍)를 학습에서 빼두고** 평가에만 쓴다
→ 사전학습 모델 그대로 vs 파인튜닝 후를 **Recall@10 · MRR** 로 비교한다
→ 숫자가 안 오르면 **사전학습 모델을 그대로 쓴다.** 학습했다는 사실보다 결과가 우선이다

> ⚠ 생성 질의는 Gemini 가 **설명을 보고 쓴** 질문이라 실제 사용자 말투와 다를 수 있다.
> 서비스를 연 뒤 진짜 질문이 쌓이면 그걸로 다시 학습하는 게 T3 다.

### T2. 리랭커 학습 — 두 번째 학습 과제

→ 임베딩은 빠르지만 거칠다. 상위 50개를 **질문과 관광지를 함께 읽는 모델**로 다시 정렬한다
→ **T1 의 학습쌍을 그대로 재사용**한다. 오답은 T1 모델이 헷갈린 것(hard negative)으로 고른다
→ T1 보다 작고 독립적이라 **실패해도 서비스에 영향이 없다.** 두 번째 학습 경험으로 적당하다

### 순서

```
1) 관광지 상세설명 선적재 배치        약 15일   ← 모든 것의 재료. 지금 시작
2) Gemini 질의 생성 (1)과 병행)      약 7~14일
3) 세라프에서 T1 학습 → 모델 다운로드   하루
4) Recall@10 비교 → 좋으면 반영        
5) T2 리랭커 (여유 있으면)
```

→ **1번이 임계 경로다.** 설명이 없으면 임베딩도 질의 생성도 할 수 없다
→ 2개월 기간 안에 1~4 는 여유 있게 들어간다
